同一份配置换到另一电脑端客户端后报错，应先判断失败发生在内核解析、图形层覆写，还是系统服务与权限，而不是反复改节点名称。下面的定位路径只使用 Clash Verge Rev 仓库描述和版本说明，适用于配置曾在某一客户端能加载，换到该应用或其不同版本、服务模式与 Sidecar 之后出现内核无法启动、TUN 不可用、DNS 异常或集合更新失败的情况。

## 适用条件

仓库说明该应用内置 mihomo，并对配置做 Merge 与 Script 增强。因此「同一配置」经过客户端后，实际送给内核的内容可能已被覆写，报错不等于原文本非法。若本机不在仓库支持的 Windows、macOS 11+ 或 Linux 架构范围内，或仍使用已不再支持的 Win7，应先排除运行环境，再谈配置定位。

## 按层缩小报错来源

第一层看进程是否真的在运行。v2.5.5 修复过内核未运行时首页仍显示服务模式，说明界面状态可以和内核不一致。后续版本优化了内核启动失败、服务模式内核意外停止的提示，会显示具体原因，并在窗口恢复后提示尚未解决的错误。v2.5.7 把服务自身运行日志保存到文件，便于追查内核被停止的原因。若完全没有内核日志，应先怀疑服务未安装、服务被强制结束，或 Sidecar 权限不足。

第二层看文件路径与权限。v2.5.5 让文件错误日志显示具体路径和失败原因，并修复不同来源订阅或规则集共用缓存路径时服务模式无法启动内核。换客户端后目录布局不同，同一订阅也会在这一层失败。Windows 上出现过系统盘删除权限误判、系统隔离权限误判、安装服务 program not found、旧版服务状态残留；macOS 有数据目录所有权、用户组解析失败、用户目录在外置磁盘、残留服务进程；Linux 有安装或修复服务后仍无法启动内核和 TUN。定位时应把报错里的路径和权限结果记下来，核对是否属于这些类别。

第三层看覆写管道。发布说明多次提到 DNS 覆写：空内容报错、初始值覆盖已有设置、已填写字段残留、空字段缺失、已填写字段被 Merge 或 Script 覆盖、Merge 覆写后旧条目仍保留、订阅含自定义 DNS 时已开启的覆写在重启后被关闭。扩展配置或脚本写入由应用设置接管的字段时，会提示并在扩展日志中记录该值已被丢弃。因此 A 客户端正常、B 客户端报错时，要检查目标侧是否启用了 DNS 覆写、Merge、Script，以及字段是否被丢弃或残留。

第四层把网络接管与内核启动分开。macOS 说明在 VPN 接管或开机网络未就绪时，服务模式内核无法启动、TUN 不可用、系统代理状态读取报错；内核意外停止后系统代理仍可能指向失效端口。Windows 与 Linux 则把 TUN 和服务模式绑在权限与服务安装上。若内核已起来但不能接管流量，应走这一层。

## 判断已经定位到哪一层

判断依据是日志是否给出文件路径或失败原因，或提示是否明确指向服务安全检查、DNS 覆写、Merge 与 Script 丢弃字段、缓存路径冲突、系统代理端口失效。v2.5.7 在 Windows 服务安全检查未通过时会说明原因；若只有笼统失败、没有路径和原因，说明尚未进入可判断状态，需要先取得服务日志。对照订阅时只比较已有链接中的 `token=示例` 这类参数是否被改写。

## 失败时下一步

分层后仍无法定位时，缩小变量：关闭 Merge、Script 与 DNS 覆写，仅保留原配置再启动；对比 Sidecar 与服务模式；避免多个订阅共用同一缓存路径。仍失败则核对是否为发布页上的 Stable 包、架构是否匹配，并阅读同一版本说明中与本操作系统对应的修复项，确认是否属于服务残留或权限误判。不要补充仓库未出现的菜单名称，也不要把内核语法错误和界面覆写当成同一类问题继续修改。
