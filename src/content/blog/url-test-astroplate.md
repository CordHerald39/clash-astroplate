把健康检查里排在前面的节点当成打开网页也会快，并不在手册给出的含义里。url 只是健康检查测试地址，timeout 只是检查超时毫秒，expected-status 只约束 HTTP 响应状态码。检查还受 lazy、interval，以及只覆盖 proxies、不覆盖 use 引入集合的限制。下面说明何时按这些字段排查、具体顺序，以及仍然对不上访问体感时下一步只做什么。

## 适用条件

本排查适用于你已经为策略组配置了 url，并且所谓最快来自该健康检查，而不是来自本页未记载的其它工具。interval 不为 0 才启用定时测试；为 0 时不应把旧状态当成当前检查。lazy 默认为 true，未选择到当前策略组时不进行测试，未被选中的组不能拿来和正在访问网页的路径对比。若节点主要写在 use 里，手册写明不会被该组 url 检查，此时任何快慢排序都不能当成这一组健康检查的结论。expected-status 默认为星号，对响应状态不做要求；一旦填写，只有状态码符合斜线或范围写法才认为可用，这与页面是否渲染完成无关。max-failed-times 默认 5，超过才强制再测，失败次数不够时排序可能尚未更新。name 必须能对应到你正在看结果的那一组，含特殊符号时应当使用引号包裹。disable-udp 只关闭该策略组 UDP，不能解释网页慢。

## 按字段排查

在开始对比网页快慢之前，先把策略组 name 与你正在使用的那一条链路对齐，接着列出 proxies 的最终成员，确认网页实际经过的出站就在其中。若流量走在嵌套的其它策略组上，仍要保证被检查的是 proxies 引入的那一层，因为 url 不会检查 use 引入的集合。然后才比较检查耗时与打开网页的体感。

第一步，确认测试目标是探测用地址。手册示例为 generate_204 这类路径，响应通常很短，不包含页面的样式、脚本、图片和后续接口。因此检查很快只说明在 timeout 毫秒内对这一地址完成了 HTTP 探测。第二步，阅读 expected-status。未配置则状态码不作为可用依据；已配置则判断依据只是状态是否落在 200/302、400-503 或混合写法内。默认星号会把各种状态都算作可完成检查，网页侧却可能遇到重定向或错误页，这会放大检查很快、页面很慢的反差。第三步，区分 timeout 与 interval：前者是单次探测何时放弃，后者是隔多少秒再测，都不是浏览器收齐文档和子资源的时间。第四步，确认被排在前面的出站是否位于 proxies；若只在集合中，不要用该组 url 解释它。第五步，确认该组当前是否被选中，避免把跳过测试后的过期印象当成当前最快。第六步，核对 filter、exclude-filter、exclude-type 是否改变了参赛名单，exclude-type 仅排除引入的出站代理且无视大小写。hidden 与 icon 只影响 API 展示，都不能解释网页慢。

## 失败时下一步

字段核对完毕访问仍然慢，应停止把健康检查排序当作整页性能。下一步仍留在手册范围内：让实际承担网页流量的出站出现在 proxies 再看检查；为探测地址补上与约定一致的 expected-status，避免任意状态都被当成可用；需要对比时不要让默认懒惰跳过当前组。不要寻找本页没有的页面加载计时项。empty-fallback 只在组为空时回退到 proxy 名称。interface-name 与 routing-mark 在代理组上已弃用，优先级为代理节点大于代理策略大于全局，与快慢体感无关。default-selected 只决定默认选谁。timeout 只覆盖探测本身，页面后续请求即使远大于该毫秒数，也不会写回健康检查结果。max-failed-times 未达到时，你看到的前列项可能仍是上一轮成功样本，和此刻网页慢可以同时成立。若问题其实是成员消失，转到 include 类开关和筛选规则确认引入集合。到此结束，不添加未记载步骤。
