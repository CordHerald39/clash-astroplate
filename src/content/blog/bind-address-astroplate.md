把监听地址改完后，本机浏览器或本机代理客户端仍可用，另一台设备却连不上，通常不是节点或分流规则先坏了，而是入站条件没有同时满足。官方对局域网访问的定义是：`allow-lan` 为 `true` 时，才允许其他设备经过 Clash 的代理端口访问互联网。`bind-address` 决定其他设备只能通过哪个地址访问：`*` 绑定所有 IP 地址；写成单个 IPv4 或单个 IPv6 时，只允许通过该地址访问。本机走回环成功，只能证明本地进程和端口还在，不能证明远端路径已被放行。

## 先确认远端访问所需的前提是否同时成立

适用条件：故障表现为「同一台主机上的客户端正常，其他主机或非本机源地址失败」。按下面顺序核对，不要跳项。

1. 读 `allow-lan`。若仍为 `false`，远端失败符合文档行为，应改为 `true` 后再测，而不是继续改绑定值。
2. 读 `bind-address`。若已从 `*` 改成某个具体地址，对端必须把代理服务器填成这个地址。
3. 确认对端源 IP 属于被允许的来源，且配置已重新加载。

判断依据是三项同时为真：允许局域网、目的地址等于绑定地址、源地址未被地址段拒绝。缺任何一项，都会出现本机可用、远端不可用。

## 核对 bind-address 与对端填写的目的地址

官方说明「仅允许其他设备通过这个地址访问」。因此改成单地址后，下列情况都会让远端失败、本机仍成功：绑定了某张网卡上的 IPv4，但对端仍填旧地址或另一块网卡的地址；绑定了单个 IPv6，而对端只尝试 IPv4；该单地址已经从接口上消失，本机却还能用 `127.0.0.1` 连本地端口。

操作步骤：在运行内核的主机上列出当前地址，确认 `bind-address` 仍存在于预期接口；让远端把服务器地址改成这一现存地址；若地址会变，将 `bind-address` 改回 `*`，使绑定覆盖所有 IP 地址。若 `ipv6` 为 `false`，内核不接受 IPv6 流量，对端仅使用 IPv6 入口时也会失败，应改走 IPv4 或打开 IPv6 接受。

判断依据：远端目的 IP 与 `bind-address` 逐字一致且该地址当前有效，才进入下一层排查；不一致就先改地址，不要先怀疑账号。

## 排查来源地址段与用户验证

`lan-allowed-ips` 仅作用于 `allow-lan` 为 `true`，默认 `0.0.0.0/0` 和 `::/0`。若改监听时把白名单收成某个网段，而远端源 IP 不在其中，连接会被拒绝。`lan-disallowed-ips` 黑名单优先级高于白名单，默认空；若写入了对端地址（文档示例为 `192.168.0.3/32` 这种主机前缀），即使白名单很宽也会失败。

若为 http(s) / socks / mixed 配置了 `authentication`，远端必须提供 `user:pass`。`skip-auth-prefixes` 允许指定 IP 段跳过验证，文档示例为 `127.0.0.1/8` 与 `::1/128`。这可以直接解释「本机不用账号、远端突然要账号」：本机命中免验证前缀，远端没有。

判断依据：源 IP 是否落在白名单、是否命中黑名单、是否既不在免验证前缀内又未携带凭据。三者任一不满足，都会在端口看起来「开着」的情况下拒绝远端。

## 仍不可达时的下一步

入站三项都正确后，把 `log-level` 调到能看到 `error`、`warning` 或更详细的 `info`/`debug`，区分认证失败与直接不可达。确认没有把 `external-controller`（文档示例为 `127.0.0.1:9090`，改成 `0.0.0.0` 才会监听所有 IP）当成代理端口来测；API 监听与代理端口是两套入口。仍失败时，到操作系统查看代理端口实际绑定的地址列表，并检查主机防火墙是否只放行了本机回环、未放行对端进来的网卡。不要用出站 `interface-name` 或 `routing-mark` 去修入站不通。
