网站策略变化，指同一主机在规则更新后走到了不同出站。官方规定规则按从上到下匹配，顶部优先。定位时不要从观感推测，而要把该网站可能触发的规则类型逐条对到更新后的列表上。本页给出的类型包括完整域名、后缀、关键字、通配符、正则、Geosite、各类 IP 与端口、进程、逻辑组合、规则集合引用和最终的 `MATCH`。下面只说明如何用这些类型定位变化，并给出失败时的下一步。

## 适用条件

适用于更新的是 `rules` 本身，或更新的是被 `RULE-SET` 引用的集合内容。目标应是一个具体网站或主机名，并且能写出它的完整域名。定位依据是“哪一条规则先匹配成功”，而不是未在文档出现的界面名称。若流量在到达域名规则前就因入站、进程、端口或用户名规则被拿走，需要先确认那些条件在更新后有没有一起改动。`IN-TYPE`、`IN-USER`、`IN-NAME`、`IN-PORT`、`PROCESS-NAME`、`PROCESS-PATH` 等都会改变命中路径，定位时必须纳入。

## 按规则类型从上到下缩小范围

步骤一：写出网站完整域名，先对 `DOMAIN`。官方示例为 `DOMAIN,ad.com,REJECT`，只有完整相等才命中。若更新前后这条是否存在或出站是否更换，能直接解释策略变化。

步骤二：对 `DOMAIN-SUFFIX`。官方说明 `google.com` 匹配 `www.google.com`、`mail.google.com` 和 `google.com`，但不匹配 `content-google.com`。更新后若新增或删除某一后缀，只有真正落在该后缀关系里的网站才会变策略。判断依据是后缀关系，而不是名字里偶尔出现同一段字符。

步骤三：对 `DOMAIN-KEYWORD`、`DOMAIN-WILDCARD`、`DOMAIN-REGEX`。通配符仅支持 `*` 和 `?`，`*` 匹配零个或多个字符，`?` 匹配一个字符，且与配置文件其他地方的 Clash 格式通配符不相同。更新后策略变化若只发生在模糊匹配，应优先怀疑这三类，而不是精确 `DOMAIN`。

步骤四：对 `GEOSITE` 与 `RULE-SET`。`GEOSITE` 匹配 Geosite 内的域名；`RULE-SET` 引用规则集合，需配置 `rule-providers`。网站策略在“只更新了集合或 Geosite 数据”后发生变化，应先看这两类在列表中的位置，再看出站是否从 `PROXY`、`auto`、`DIRECT` 或 `REJECT` 被改写。

步骤五：对 IP 类与 `GEOIP`。`IP-CIDR` 与 `IP-CIDR6` 效果一样，后者只是别名。还有 `IP-SUFFIX`、`IP-ASN`、`GEOIP`。域名开始匹配目标 IP 规则时会触发 DNS 解析，可用 `no-resolve` 跳过。若更早匹配已触发解析，带 `no-resolve` 的目标 IP 规则依旧会匹配。`src` 将目标 IP 匹配转为来源 IP 匹配。网站策略变化若伴随解析行为变化，应把附加参数列入定位范围。

步骤六：若以上都不中，看 `MATCH`。它匹配所有请求、无需条件。更新后把 `MATCH` 的出站改掉，或把某网站从前面规则中删除导致掉进 `MATCH`，都会表现为整个网站策略变了。

## 排除 UDP 与逻辑规则造成的假变化

如请求为 udp，而代理节点没有 udp 支持，则会继续向下匹配。看起来像网站策略变了，实际是同一条代理规则被跳过。逻辑规则为 `AND`、`OR`、`NOT`，需要注意括号，例如 `AND,((DOMAIN,baidu.com),(NETWORK,UDP)),DIRECT`。`SUB-RULE` 也要注意括号。更新后只改了括号或逻辑类型，网站域名没变，策略仍会变。判断依据是：先固定域名，再看 `NETWORK`、逻辑组合和子规则是否在更新中被改写。

## 失败时下一步

若仍不能定位：把该网站从列表顶部逐条对照，记录第一条应当命中的类型与出站，再与更新前的同一位置比较，区分是“规则被插入、删除、改出站”还是“集合内容变了但 `RULE-SET` 行没变”。若对照结果指向 `RULE-SET` 但名称无法对应 `rule-providers`，先修引用。若指向 IP 类，核对是否因 DNS 已解析或 `no-resolve`、`src` 使命中从域名规则换成地址规则。若所有具名规则都不中，检查 `MATCH` 是否被移动或改出站。
