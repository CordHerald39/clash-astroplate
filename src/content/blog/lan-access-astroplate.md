同一 Wi-Fi 下另一台设备连不上本机 Clash 代理时，优先按全局配置里与局域网入站有关的项逐条对照，而不是先怀疑「是不是没连上同一个热点」。官方说明里，其他设备能否经过代理端口访问互联网，由 `allow-lan`、`bind-address`、`lan-allowed-ips`、`lan-disallowed-ips` 以及代理认证共同决定。下面按故障现象给出适用条件、操作和判断依据。

## 先区分「未开放局域网」和「开放了但绑错地址」

适用条件：对端与运行 Clash 的主机在同一二层网络，对端已把代理主机、端口指到你认为正确的位置，但连接被拒绝、超时或根本打不到服务。

操作步骤：

1. 检查 `allow-lan`。该项可选 `true`/`false`。文档定义是：允许其他设备经过 Clash 的代理端口访问互联网。若为 `false`，同一 Wi-Fi 也不能使用这些代理端口。
2. 若已为 `true`，立刻核对 `bind-address`。它表示仅允许其他设备通过这个地址访问。`"*"` 表示绑定所有 IP；也可写成单个 IPv4（文档示例 `192.168.31.31`）或单个 IPv6（文档示例 `[aaaa::a8aa:ff:fe09:57d8]`）。
3. 在运行 Clash 的主机上查看当前 Wi-Fi 地址，确认对端填写的代理地址与 `bind-address` 实际绑定的地址一致。

判断依据：

- `allow-lan` 为 `false`：故障原因在总开关，改网段名单不会让对端连上。
- `bind-address` 为某个具体 IPv4，而主机当前地址已变成另一个地址：对端即使用对了「以前的局域网 IP」也会失败。
- `bind-address` 只绑了 IPv4，对端却走 IPv6（或相反）：属于绑定范围不包含对端所用协议栈。此时还要看 `ipv6`（可选 `true`/`false`，默认 `true`）是否允许内核接受 IPv6 流量。

失败时下一步：先把 `allow-lan` 设为 `true`，并把 `bind-address` 改成当前仍有效的地址或 `"*"`，重新加载后再测。不要在地址已过期时去改代理协议类型。

## 再核对白名单、黑名单是否把对端 IP 排除在外

适用条件：总开关已打开，绑定地址也能从本机看到，但对端特定设备仍失败，而你可能只测过网关或另一台机器。

`lan-allowed-ips` 是允许连接的 IP 地址段，仅在 `allow-lan` 为 `true` 时生效，默认 `0.0.0.0/0` 和 `::/0`。`lan-disallowed-ips` 是禁止连接的 IP 地址段，黑名单优先级高于白名单，默认空；文档示例为 `192.168.0.3/32`。

操作步骤：

1. 取得无法连接那台设备的 IPv4/IPv6。
2. 检查它是否落在 `lan-allowed-ips` 内。若你把默认的 `0.0.0.0/0`、`::/0` 收窄成某一段，同一 Wi-Fi 里不在该段的地址会被拒绝。
3. 再检查 `lan-disallowed-ips`。只要对端被黑名单命中，即使白名单是全网段也会失败。
4. 若只失败 IPv6 或只失败 IPv4，分别对照对应前缀，不要用一种地址的成功去推断另一种。

判断依据：同一 Wi-Fi 不等于同一允许网段。黑名单优先，因此「默认允许全部」不能覆盖「显式禁止某一主机」。

失败时下一步：临时把对端 IP 从 `lan-disallowed-ips` 去掉，或把它明确写入 `lan-allowed-ips` 对应前缀，重新加载后再测。仍失败再进入认证检查，避免同时改很多项导致无法归因。

## 排除代理认证和对端填错端口这两类「能碰到端口却进不去」

适用条件：日志或连接表现已经能碰到代理端口，但对端提示需要认证、代理拒绝或协商失败。

文档中，`authentication` 为 http(s) / socks / mixed 代理的用户验证，列表项格式为 `user1:pass1`。`skip-auth-prefixes` 设置允许跳过验证的 IP 段，示例为 `127.0.0.1/8` 和 `::1/128`。

操作步骤：

1. 查看配置是否存在 `authentication`。若存在，同一 Wi-Fi 的设备默认也要提供列表中的用户名和密码。
2. 确认对端 IP 是否出现在 `skip-auth-prefixes` 中。仅回环地址在示例范围内，局域网地址通常不在其中。
3. 确认对端使用的是 Clash 的代理端口，而不是 `external-controller`（文档示例为 `127.0.0.1:9090`，并可改为 `0.0.0.0` 以监听所有 IP）。外部控制是 RESTful API，与「其他设备经过代理端口访问互联网」不是同一条路径。

判断依据：认证失败时，问题不在 `allow-lan` 是否为真，而在凭据或跳过网段。把 API 地址当成代理主机填给另一台设备，会表现为「连上一个端口但不是代理」。

失败时下一步：在对端按 `authentication` 提供凭据，或把该设备网段谨慎加入 `skip-auth-prefixes` 后重试。若对端连的是 API 端口，改回代理端口。若以上均已匹配仍失败，回到 `bind-address` 与当前 Wi-Fi 地址是否一致，因为地址变化会让「看起来在同一 Wi-Fi」的配置同时失效。
