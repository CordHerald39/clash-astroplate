当 Clash 看起来“几乎没有日志”，因而无法从输出里定位原因时，优先核对日志级别、输出位置和配置是否被真正加载，而不是先假设内核没有工作。官方把日志等级写在全局配置的 `log-level`，并限定这些内容仅在控制台和控制页面输出。日志太少，通常是级别过低、输出位置看错，或配置未生效，需要按定义逐项排除。

## 适用条件：什么叫“日志太少”

本检查适用于：你已经在尝试复现问题，但控制台或控制页面几乎空白；只有极少量记录，对不上当前失败；或你不确定当前到底开的是哪一档。若不打算看内核输出，或当前环境根本没有控制台和控制页面，改级别没有可观察结果，应先解决“能看到官方指定的两处输出”。

官方对级别的收录范围是判断“少得是否正常”的唯一依据。silent 为静默、不输出，此时“完全没有日志”是符合定义的，不能当成故障本身。error 仅输出发生错误至无法使用的日志，若当前只是不影响运行的异常，error 下为空也符合定义。warning 才会输出发生错误但不影响运行的日志，并带上 error 内容。info 才会输出一般运行的内容，并覆盖 error 与 warning。debug 才会尽可能输出运行中所有的信息。文档示例为 `log-level : info`。因此，日志少并不自动等于配置错误，首先要看当前取值是否本来就不该有一般运行内容。

## 按级别定义逐项检查

第一步，读出当前全局配置里的 `log-level`。若是 silent，结论已经明确：内核按设计不输出，必须改成 error、warning、info 或 debug 之一，否则后面所有“找原因”都没有材料。若是 error，只在“错误至无法使用”时才有记录；现象若是能运行但行为不对，应改为 warning，再复现一次。若已是 warning 仍几乎没有内容，说明可能连“不影响运行的错误”也未按该级别产生，需要升到 info，以确认一般运行内容是否出现。

第二步，确认观察位置。官方写明日志仅在控制台和控制页面输出。若你在其他位置寻找文件或副本，即使级别正确也会误判为“太少”。判断依据是：同一时间复现同一操作，只有控制台或控制页面出现与级别相符的新增行，才算看到了内核日志。

第三步，对照“有没有一般运行内容”来决定要不要升到 info 或 debug。info 的职责是输出一般运行的内容以及更低级别日志；若你需要知道流程是否走过，而当前只有偶发错误行，应使用 info。仅当 info 已经有一般运行内容，但仍无法解释失败路径时，才使用 debug，因为它会尽可能输出运行中所有的信息。不要在尚未排除 silent/error 的情况下直接开 debug，否则难以分辨“以前是被级别滤掉”还是“本来就没有那类事件”。

## 仍看不到原因时的下一步

若已经改为 info 或 debug，且确认正在看控制台或控制页面，输出仍然少到无法解释问题，下一步检查配置是否被当前内核使用：`log-level` 拼写是否为 silent、error、warning、info、debug 之一；是否误把其他副本里的旧值当成正在运行的值；修改后是否已对当前进程生效。生效的判断仍是输出变化：从 silent 改为 info 后应出现一般运行内容；从 error 改为 warning 后应可能出现不影响运行的错误。

若升级后瞬间出现大量信息，说明此前“太少”是级别过滤，应按新内容解读，而不是继续加级别。若升级后仍然完全空白，回到输出位置和配置加载问题，而不是发明额外的日志开关——官方在全局配置中只提供这一项日志等级，并且只承诺控制台与控制页面。能定位原因后，把级别从 debug 降回 info 或你日常使用的档位，避免继续以“尽可能所有信息”作为常态。
