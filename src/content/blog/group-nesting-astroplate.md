## 适用条件

策略组可以通过 `proxies` 引入其他策略组，因此会出现组与组互相指向、或一条引用链回到自身的情况。官方文档没有把“互相引用”写成单独的报错码，排查时应回到字段约束：每个组必须有 `name` 与 `type`；`proxies` 引入出站代理或其他策略组；`use` 引入代理集合；若干“引入全部”开关按名称排序且不包含策略组；空组回退与健康检查各有明确边界。适用于配置加载后成员为空、默认节点不是预期对象、或嵌套组无法落到出站代理等异常，而不是去推测未记载的界面提示。

## 按字段逐项排查

先做名称核对。`name` 含特殊符号时应当使用引号包裹。互相引用时，一边漏了引号、一边没漏，看起来是“两个组互相写了对方”，实际是名字根本不是同一个键。确认每个被引用的名字都能在策略组列表里找到对应项，且没有把出站代理、代理集合、策略组三类名字混用在错误字段里。

再看引入方向是否合法。只有 `proxies` 能挂其他策略组。`include-all`、`include-all-proxies` 明确写了引入不包含策略组；需要嵌套时仍应写在 `proxies`。`include-all-providers` 会引入全部代理集合并让“引入代理集合”失效，若异常表现为集合成员突然消失或顺序按名称重排，应优先查这个开关，而不是先怀疑环引用。`use` 只接代理集合，把策略组名填进去不会变成合法的组嵌套。

接着查空组与默认选择。`default-selected` 为空或节点名不存在时，默认选择组中第一个节点；若互相引用导致某一层展开后没有任何出站代理，所谓“第一个节点”也会落空。`empty-fallback` 默认 `COMPATIBLE`，且不支持填写代理组、只支持填写 proxy 名称。把另一策略组名当作空组回退，属于文档已排除的写法，应改成真实 proxy。`filter`、`exclude-filter` 仅作用于引入代理集合以及引入所有出站代理，多个正则可用反引号区分；`exclude-type` 用 `|` 分割、不支持正则，只排除引入的出站代理。筛选把叶子滤空后，嵌套组会表现为“还能看见组名、底下没有可用代理”。

健康检查异常要和引用异常分开。`url` 只检查 `proxies` 里的代理，不检查 `use` 引进的集合。`interval` 不为 0 才定时测试；`timeout` 单位为毫秒；`max-failed-times` 默认 5，超过则触发一次强制健康检查；`lazy` 默认 true，未选择到当前策略组时不测；`expected-status` 默认为 `*`，配置后必须匹配状态码才视为可用。集合成员从未被该组 `url` 检查，不能据此判断“互相引用导致探测失败”。

## 判断依据与失败后的下一步

判断引用是否异常，依据是：每个组名唯一且引号一致；策略组只出现在其他组的 `proxies` 中；每条引用链最终能落到出站代理，而不是只在组与组之间打转；空组只回退到 proxy。若仍异常，下一步应去掉不该存在的组名引用、把 `empty-fallback` 改为 proxy、检查筛选是否清空叶子，并核对 `include-all-providers` 是否破坏了集合引入。不要在组上继续使用已弃用的 `interface-name` 与 `routing-mark` 去解释连通性，二者应写在代理节点，优先级为代理节点大于代理策略大于全局。`hidden` 只让 API 隐藏展示，不会修复错误的互相引用。
