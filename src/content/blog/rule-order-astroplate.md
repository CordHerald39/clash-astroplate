## 适用条件与现象界定

在 MetaCubeX/mihomo 手册的路由规则里，`rules` 是有序列表。官方写明：规则将按照从上到下的顺序匹配，列表顶部的规则优先级高于其底下的规则。因此“后面的规则始终不命中”应先按截断理解：本次请求已在上方命中第一条成立的规则，匹配结束，下方条目不会再被求值。它通常不是“后半段语法失效”，而是更靠前的条件已经为真。

适用条件是列表中同时存在多条可能覆盖同一请求的规则，尤其含 `DOMAIN-KEYWORD`、`GEOSITE`、`GEOIP`、`RULE-SET` 或 `MATCH`。判断依据是：固定同一目标（同一主机名、端口和传输层），实际出站始终等于某条靠前规则的策略名，你期望的靠后规则从未成为结果。必须分开的一种情况是 UDP：如请求为 udp，而代理节点没有 udp 支持（例如 ss 节点没写 udp: true），则会继续向下匹配。那是“命中后出站能力不足再往下走”，不能解释成后规则被跳过。

## 具体操作与类型判断依据

把当前 `rules` 按文件顺序编号。针对一条可重复请求，记下完整域名、目标端口、来源端口、入站类型与名称、进程名或路径、tcp 还是 udp，以及是否已有目标 IP。然后从上到下用手册类型判断该条是否为真，停在第一条为真的规则。该条的出站就是当前最终策略，也是后规则“没有机会”的直接原因。

判断必须按类型定义，而不是按名称想象。`DOMAIN` 匹配完整域名。`DOMAIN-SUFFIX` 匹配域名后缀：`google.com` 匹配 `www.google.com`、`mail.google.com` 和 `google.com`，但不匹配 `content-google.com`。`DOMAIN-KEYWORD` 做关键字匹配，覆盖通常更宽，容易提前截走流量。`DOMAIN-WILDCARD` 仅支持 `*` 和 `?`，`*` 匹配零个或多个字符，`?` 匹配一个字符，且与配置文件其他地方的 Clash 格式通配符不相同。`DOMAIN-REGEX` 按正则匹配域名。`GEOSITE` 匹配 Geosite 内的域名。`IP-CIDR` 与 `IP-CIDR6` 效果一样，后者只是别名；另有 `IP-SUFFIX`、`IP-ASN`、`GEOIP`。域名开始匹配关于目标 IP 的规则时，mihomo 将触发 dns 解析来检查目标 IP；可以选择 `no-resolve` 跳过解析。如在更早的匹配中触发了 dns 解析，则依旧会匹配到添加了 `no-resolve` 选项的目标 IP 类规则。`AND`、`OR`、`NOT` 与 `SUB-RULE` 都需要注意括号。`MATCH` 匹配所有请求、无需条件，写在中部会吞掉其后全部规则。`RULE-SET` 在引用位置插入集合内规则，集合本身也能成为截断点。

操作时重点核对“宽规则在前、细规则在后”：关键字或 Geosite 压住后缀；入站、端口、进程条件先成立；`OR` 过宽或 `NOT` 取反范围过大。这些都会让后写细规则看起来永不命中。

## 失败时下一步

若第一条为真的规则仍对不上现象，把列表缩成三条：一条可疑宽规则、一条你期望命中的细规则、以及最后的 `MATCH`，对同一目标再发起请求。细规则仍不出现时，检查 `MATCH` 是否被提前放置、逻辑括号是否与手册示例一致（例如 `AND,((DOMAIN,baidu.com),(NETWORK,UDP)),DIRECT`），以及上方是否已引用会覆盖同一目标的 `RULE-SET`。缩小后细规则能成为结果，再按原顺序逐条加回，定位真正的截断点。涉及目标 IP 时，要核对解析是否已被更早规则触发，不能只给后写的 `IP-CIDR` 增加 `no-resolve`。进程路径、UID、DSCP、入站用户名等受平台和入站类型限制，条件不成立时应改条件或位置，而不是在后半段重复堆叠同目标规则。定位后把更具体的规则上移，或收窄过宽规则。
