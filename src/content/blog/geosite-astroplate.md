当 Clash 的域名分类规则没有包含目标网站时，该请求不会在 GEOSITE 这一行停下，而是继续按列表向下匹配。官方将 GEOSITE 定义为匹配 Geosite 内的域名，因此分类未收录就等于这一条不成立。处理办法是改用官方已列出的其他域名规则，或在完成 rule-providers 后改用 RULE-SET，并始终遵守从上到下的优先级。本文只解答「分类没包含目标网站时怎么办」，不假设某个分类名应当覆盖哪些站点。

## 适用条件与如何判断「没包含」

适用条件有两点同时成立：配置里已经写了 GEOSITE；目标网站的主机名按当前规则顺序没有在该分类行命中，而是落到更靠后的规则，尤其是 MATCH。MATCH 匹配所有请求、无需条件，所以「没包含」最常见的可观察结果是：请求没有停在分类行，最终被 MATCH 指定的出站接收。

判断时先排除「其实被前面的规则截走」。规则将按照从上到下的顺序匹配，顶部优先级更高。若目标在 GEOSITE 之前已命中 DOMAIN 或 DOMAIN-SUFFIX，那不是分类未收录，而是更具体的规则先成立。只有确认分类行被问到、却仍不成立，才能判定为 Geosite 内没有该域名。GEOSITE 也不处理 IP 国家代码、端口、进程或入站类型；目标若根本不是域名，应改看 GEOIP、DST-PORT、PROCESS-NAME、IN-TYPE 等类型，而不是在域名分类里查找。

官方示例中的逻辑规则使用 DOMAIN,baidu.com 这类字面条件。当分类未收录时，也可以把目标从分类名改回这种可逐条审查的 payload，再视需要与 NETWORK 等条件组合。

## 用字面域名规则补上目标网站

分类未包含目标时，优先在 GEOSITE 之前增加字面规则，保证该站点不再依赖分类数据。完整主机名用 DOMAIN。只需要覆盖自身及子域时用 DOMAIN-SUFFIX；官方对后缀的匹配边界是明确的：写成 google.com 会匹配 www.google.com、mail.google.com 和 google.com，但不匹配 content-google.com。若目标网站的主机名只是「包含某段字符」而不是后缀关系，应改用 DOMAIN-KEYWORD，避免误用后缀规则。

主机名结构不规则时，可以使用 DOMAIN-WILDCARD 或 DOMAIN-REGEX。通配符仅支持 * 和 ?，* 匹配零个或多个字符，? 匹配一个字符；官方同时注明，这里的通配符和配置文件其他地方的 Clash 格式通配符不相同。正则则按 DOMAIN-REGEX 的表达式匹配。选择哪一种，判断依据是你能否用官方定义准确描述目标主机名，而不是分类名是否「看起来接近」。

这些补写行必须放在 MATCH 之前，也通常应放在原来的 GEOSITE 之前，否则分类未命中后仍可能被其他宽泛规则先接走。需要引用一整组可维护的域名列表时，使用 RULE-SET,providername,proxy 这一官方形式，并配置 rule-providers；未配置提供者就写 RULE-SET，不能当作已经补上目标网站。

## 组合条件、失败排查与下一步

若目标网站只在特定协议或端口下才需要不同于默认的出站，不要指望分类名内部区分这些条件。官方提供 AND、OR、NOT：LOGIC_TYPE,((payload1),(payload2)),Proxy，其中 payload 为规则类型和其他 payload，例如 DOMAIN 与 NETWORK 的组合，并需要注意括号。SUB-RULE 用于匹配至子规则，同样要注意括号。分类未收录时，把目标网站写成这些逻辑规则中的域名 payload，比继续更换分类名更符合官方类型定义。

补写后仍失败，按下列依据排查：第一，新规则是否写在被截走的位置之下，导致从未执行到；第二，DOMAIN 与 DOMAIN-SUFFIX 是否用错，完整主机名被当成后缀，或后缀写成了不会命中的那种子串；第三，通配符是否用了官方未支持的语法；第四，目标实际是 IP 匹配问题，需要 IP-CIDR、IP-CIDR6、IP-SUFFIX 或 GEOIP，而不是域名分类。涉及目标 IP 规则时，记住域名开始匹配这类规则会触发 dns 解析，可用 no-resolve 跳过；但更早的匹配若已触发解析，带 no-resolve 的目标 IP 规则仍可能命中。

若请求为 udp 且当前出站没有 udp 支持，官方说明会继续向下匹配。目标网站「分类未包含」与「因协议被跳过」要分开处理：前者补域名规则，后者检查该行出站是否适用于 udp，而不是继续追加 GEOSITE。仍无法落到指定出站时，用字面规则把该站点固定在 MATCH 之前，停止以未收录的分类名作为唯一条件。
