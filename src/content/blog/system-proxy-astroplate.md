系统代理开启，只表示操作系统把 HTTP/HTTPS 代理指向了 Clash 的 http 或 mixed 入站。某个应用仍表现为不走代理，需要先判断流量有没有进进入站，再判断进了之后被 mode 怎样处理。官方全局配置可用来核对的是用户验证、绑定与局域网策略、运行模式、日志、外部控制，以及进程匹配模式的真实含义。不要把系统代理开关理解成所有应用、所有协议的强制入口。

## 先分开两层现象

第一层：应用有没有把流量送到 Clash 入站。只有遵守系统 HTTP/HTTPS 代理，或被手动填写同一 http/socks/mixed 端口的应用，才会走这条路径。自带网络栈、忽略系统代理、只建立普通套接字的程序，可以完全不询问系统代理。此时内核规则再完整，也不会留下该应用的连接记录。

第二层：流量已经进入入站后如何处置。mode 为 rule 时按规则匹配；global 时走 GLOBAL 策略组，且需要在该组选择代理或策略；direct 为全局直连。应用其实已经连上入站、但 mode 为 direct 时，表现仍是不走代理节点，日志里应能看到连接被直连处理，而不是完全空白。

find-process-mode 容易被误当成强制所有应用走代理。文档定义是：always 强制匹配所有进程，strict 为默认并由 Clash 判断是否开启，off 不匹配进程、推荐在路由器上使用。它用于规则侧识别进程，前提是流量已经到达内核。它不能把一个不使用系统代理的应用自动导入 http 入站。若只开启了系统代理、没有其他抓取路径，却指望靠进程名把某应用拉进来，检查方向就不对。

## 按配置项检查

先看 authentication 与 skip-auth-prefixes。http(s)/socks/mixed 可配置多组用户名和密码。本机源地址多为 127.0.0.1 或 ::1，文档示例将 127.0.0.1/8、::1/128 列为可跳过验证的前缀。应用走系统代理但未携带认证、又未命中跳过前缀时，入站会拒绝连接，看起来像应用不走代理。

再看 bind-address 与 allow-lan。允许局域网为 true 时，其他设备才应经代理端口访问互联网。bind-address 为 * 表示绑定所有 IP，也可绑定单一 IPv4 或 IPv6。lan-disallowed-ips 黑名单优先于 lan-allowed-ips。本机应用连接 127.0.0.1 上的入站时，应优先查端口是否一致以及认证是否放行，而不是先放宽局域网策略。

然后看观测通道。将 log-level 设为 info 或 debug，在控制台或控制页面观察该应用发起请求的瞬间有无新连接、有无认证错误。silent 无法用于排查。再用 external-controller 读取内核状态，文档示例为 127.0.0.1:9090，可配置 secret。确认当前 mode、策略组选择和连接列表。profile.store-selected 为 true 时会保存 API 对策略组的选择。API 始终看不到该应用，说明请求未进 Clash；能看到但出口为直连，则应回到 mode 与规则，而不是反复开关系统代理。

## 判断依据和失败后的下一步

判断依据可以收成三条。系统代理开启后，应用发请求时日志与 API 均无记录：判定为未使用系统代理，或主机端口指向错误。有记录且 mode 为 direct：判定为内核按全局直连处理。有认证失败记录：判定为入站拒绝，而不是节点未选中。ipv6 默认 true，仅在 IPv6 目标异常时再核对该项。

下一步按判定执行。对不遵循系统代理的应用，只开系统代理无法覆盖，需要该应用支持手动 HTTP 或 SOCKS，或改用其他入站方式；不要指望单独把 find-process-mode 改为 always 来解决问题。对已进入入站的流量，把 mode 从 direct 改回 rule 或 global 再对比；global 时确认 GLOBAL 组已选择代理。认证问题先调整 skip-auth-prefixes，或为应用提供同一组用户验证。仍无线索时开 debug，并确认 API 的访问方式与 secret 符合文档；经 Unix socket 或 Windows namedpipe 访问时不会验证 secret，需注意安全。
