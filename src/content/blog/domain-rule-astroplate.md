配置里写了主域名，子域名请求却仍落到别的策略，多半不是“规则没生效”，而是规则类型本身只认完整主机名。MetaCubeX/mihomo 手册把 `DOMAIN` 定义为匹配完整域名，把 `DOMAIN-SUFFIX` 定义为匹配域名后缀。前者要求请求主机与载荷逐字相等；后者才按后缀关系覆盖该后缀本身以及更长的子域名。二者不能互相替代。

## 适用条件：何时主域名盖不住子域名

满足下面任一条件时，写主域名都不会自动覆盖子域名：

- 规则类型是 `DOMAIN`。手册写明它匹配完整域名。`google.com` 只对主机恰好为 `google.com` 的请求成立，`www.google.com`、`mail.google.com` 因主机名不同而不命中。
- 规则类型虽是后缀类，但载荷写成了另一个标签，而不是可叠加的后缀。手册举例：`DOMAIN-SUFFIX` 的 `google.com` 匹配 `www.google.com`、`mail.google.com` 和 `google.com`，但不匹配 `content-google.com`。连字符连在一起的名字不是“点分后缀”关系。
- 列表里更靠前的规则已经先命中。规则按从上到下的顺序匹配，顶部优先级更高。子域名可能先被 `DOMAIN-KEYWORD`、`GEOSITE`、`RULE-SET` 或逻辑规则拿走，后面的主域名条目根本轮不到。
- 把通配符规则和后缀规则当成同一套语义。`DOMAIN-WILDCARD` 仅支持 `*` 与 `?`，`*` 匹配零个或多个字符，`?` 匹配一个字符，且与配置文件其他地方的 Clash 格式通配符不相同。写错位置时，既盖不住主域名，也盖不住预期的那一层子域名。

适用结论可以收成一句：只有需要“主机名完全等于这一条”时才用 `DOMAIN` 写主域名；需要“该后缀及其子域名走同一策略”时必须改用 `DOMAIN-SUFFIX`，并且后缀要落在标签边界上。

## 具体场景：按请求主机逐步判断

以请求主机 `www.google.com`、配置中写了 `google.com` 为例，按顺序做判断，不要跳步：

1. 打开 `rules` 列表，从第一条开始往下读，找到所有载荷含 `google.com` 或可能命中该主机的条目，记下它们的类型和先后位置。
2. 若第一条相关规则是 `DOMAIN,google.com,策略名`，判断依据是完整相等。`www.google.com` 不等于 `google.com`，本条跳过，继续向下。这就是“写了主域名却没覆盖子域名”的典型路径。
3. 若相关规则是 `DOMAIN-SUFFIX,google.com,策略名`，判断依据是：主机等于该后缀，或以英文句点加上该后缀结尾。手册明确 `www.google.com`、`mail.google.com` 和 `google.com` 都会匹配。此时若仍未覆盖，原因通常不在类型，而在顺序或后面的逻辑规则。
4. 用反例复核边界。把主机换成 `content-google.com`：按手册，它不应被 `DOMAIN-SUFFIX,google.com` 命中。若你的预期是“名字里出现 google 就算”，应改看 `DOMAIN-KEYWORD`，而不是抱怨后缀规则。
5. 检查逻辑规则括号。手册给出 `AND,((DOMAIN,baidu.com),(NETWORK,UDP)),DIRECT` 这类写法，并强调要注意括号。括号缺失或载荷类型写错时，整条可能无法按设想参与匹配，子域名会落到更靠后的规则或 `MATCH`。
6. 排除 IP 类规则的干扰。`IP-CIDR`、`GEOIP` 等是匹配目标 IP；域名开始匹配这些规则时，mihomo 可能触发 DNS 解析来核对目标 IP。这与 `DOMAIN` 不覆盖子域名是两件事。若子域名最终因解析后的 IP 命中了 `GEOIP` 或 `IP-CIDR`，应回头看规则顺序，而不是给 `DOMAIN` 加“自动含子域”的想象。

判断依据始终回到手册原句：完整域名对完整主机；域名后缀对后缀关系，且不以“字符串包含”代替“标签后缀”。

## 失败时下一步

若按上面核对后，子域名仍未进入你为该主域名准备的策略，按下列顺序改，一次只改一类问题：

- 确认目标是覆盖子域名后，将对应条目从 `DOMAIN` 改为 `DOMAIN-SUFFIX`，载荷继续写主域名，不要把某一级主机前缀写进后缀，除非你只想覆盖更深的一层。
- 把更具体的完整主机规则放在更宽的后缀规则之前，避免子域名先被宽规则或关键字规则截走。
- 若只要一层通配、不要误伤其他后缀，改用 `DOMAIN-WILDCARD`，并按手册核对 `*`、`?` 的含义，不要套用其他字段的通配符习惯。
- 模式更复杂时再用 `DOMAIN-REGEX`，同时确认正则是否锚定到点分边界，避免把 `content-google.com` 一类名字误收进来。
- 核对列表末尾的 `MATCH`。未命中的请求会落到这里；若子域名总是走 `MATCH` 的策略，说明前面没有任何域名规则真正命中它。
- 涉及 `RULE-SET`、`SUB-RULE` 时，确认引用名称与括号写法与手册一致，避免子规则根本没被进入。

不要根据客户端界面上的观感推断“主域名会自动带子域”。以手册中 `DOMAIN` 与 `DOMAIN-SUFFIX` 的定义为唯一判断标准，用请求主机逐条对照类型和顺序即可定位。
