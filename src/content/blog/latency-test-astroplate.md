健康检查结果里出现超时，只说明这一次探测没有在限定时间内得到合格响应。它不等于该出站已被内核永久剔除，也不等于 `select` 一类策略组不能再点选该节点。是否还能使用，要看检查范围、期望状态、懒惰测试和失败计数，而不是只看「超时」这个展示口径。

## 适用条件：timeout 在资料里管什么

`timeout` 表示健康检查超时时间，单位毫秒。它约束的是这一次探测最多等多久，资料没有把它写成「超时后禁止手动选择」或「超时后从列表删除」。真正发起检查的地址是 `url`，并且同样只会检查 `proxies` 字段里的代理，不会检查通过 `use` 引入的代理集合。因此界面或 API 上的超时，要先分清是组级健康检查的结果，还是集合自己的状态，二者不能混为一谈。

若配置了 `expected-status`，则只有响应状态码与期望一致时才认为节点可用；默认为 `*`，对响应状态不做要求。超时通常意味着时限内没有拿到可判定的响应，这与「已经返回但状态码不在允许集合」不是同一类失败。`max-failed-times` 默认 5，超过才触发一次强制健康检查，说明失败会被累计，但不等于计一次超时就停用该出站。

## 超时不能直接等同于无法使用的判断依据

依据一：超时是健康检查等待用尽，资料未规定超时节点从 `proxies` 消失。策略组仍按 `type` 与成员列表工作，超时改变的是这次检查是否记为成功。依据二：`lazy` 默认为 true，未选择到当前策略组时不进行测试。此时展示里的旧超时、空值或未刷新数字，不能用来断言当前不可用。依据三：`default-selected` 只在为空或节点名不存在时改选组内第一个节点，与延迟是否超时无直接因果关系。依据四：`empty-fallback` 只在组为空时回退到某个 proxy 名称，健康检查超时不会把组变成空组，也不能把超时节点理解成「组已空」。依据五：经 `use` 进入的节点本就不被该组 `url` 检查，它们显示超时或尚未检查，不能据此说该出站不能用来转发。

还要区分两种「不合格」：时限内无响应，以及有响应但 `expected-status` 不匹配。后者即使很快返回，仍会被判不可用；前者把 `timeout` 调大后仍可能在状态码规则下失败。默认 `*` 时，资料不对状态码提要求，超时更不宜直接读成业务层切断。

## 仍被当成不可用时的下一步

先读该组完整检查条件：`url`、`timeout`、`expected-status`、`interval`、`lazy`、`max-failed-times`。若 `expected-status` 写成了测试地址不会返回的码，节点会一直被判不可用，应改成单码、斜线连接的多码或短横连接的范围，或回到默认 `*`。资料允许的混合写法包括 `200/302` 与 `200/302/400-503` 这类形式。若 `timeout` 过小，只说明等待不够，应在调整毫秒数后再观察失败次数是否已到 `max-failed-times` 从而触发强制检查。

节点来自 `use` 时，不要用该策略组上的组级超时解释集合内延迟。组级 `interface-name` 与 `routing-mark` 已弃用，出站网卡或路由标记应以节点字段为准，优先级为代理节点大于代理策略大于全局，避免把超时误判成组级绑网失败。只有组真的为空时才轮到 `empty-fallback`，且不能填写代理组。处理顺序应是：分清检查范围，核对期望状态，再调整等待时间，最后看失败次数与懒惰状态，而不是一看到超时就删节点。
