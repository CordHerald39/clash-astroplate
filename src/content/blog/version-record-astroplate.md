网上 Clash 教程里的菜单、侧栏和按钮位置经常对不上你手头的界面。这通常不是“你装错了”，而是教程在讲某一封装的图形外壳，而可核对的官方说明写的是 mihomo 内核全局配置。核对客户端名称和版本时，应以手册中的标识与字段为准，而不是以截图是否相似为准。

## 适用条件：界面教程不能当作核验基准

当你发现教程中的菜单结构、用词或层级与当前窗口不一致时，先停止按截图逐项寻找。MetaCubeX/mihomo 手册的全局配置章节给出的是 `allow-lan`、`mode`、`log-level`、`external-controller`、`external-ui` 等键名，没有规定某一 Clash 客户端必须把这些项放在哪个菜单下。因此，“教程有某菜单、本地没有”不能直接推断版本过低或名称错误。

适用对象是：能打开配置文本或至少能看到与内核相关的控制页面，并愿意用字段名而不是界面文案来核对。若完全无法查看 YAML，只能把界面差异记录为“外壳不同”，无法在本页资料下完成名称核验。

## 用内核字段核对，而不是用菜单名称

可操作的判断依据是配置里是否出现该手册定义的项，以及取值是否落在文档给出的集合内：

- 运行模式是否为 rule、global、direct 之一（默认规则模式）。global 还要求在 GLOBAL 策略组中选择代理或策略，这是内核语义，不一定对应教程里某个开关的名字。
- 日志是否按 silent / error / warning / info / debug 分级，并且只在控制台和控制页面输出。若教程把日志画在别的面板，以手册为准。
- 是否存在 `external-controller`、CORS、`secret`，以及 Unix socket、Windows namedpipe、`external-controller-tls` 等 API 监听方式。教程若只画“打开仪表板”，没有区分这些监听形态，界面必然对不上。
- 是否配置 `external-ui`（静态网页资源，路径为 API 地址 `/ui`）。这是内核挂载的外部用户界面，可以自定义 `external-ui-name`、`external-ui-url`，与客户端主窗口不是同一层。

名称核对应优先对齐手册中的项目名：内核侧为 mihomo；外部资源下载默认 UA 为 `clash.meta`。后者只是 `global-ua` 的默认值，不能当成窗口标题或商店里的应用名。若教程把软件叫 Clash、Clash Meta 或其他商业名，而配置模型与上述字段一致，应在记录中写“外壳名称（教程用名）+ 内核按 mihomo 全局配置”，避免只保留一个容易冲突的商品名。

## 版本相关的可核验信号

本页没有为各图形客户端规定版本号格式，但提供了可用来排除错误对照的信号。TLS 中本地证书、私钥或 ECH 密钥的自动重载自 v1.19.18 才支持；教程若把“改证书即生效”写成某菜单里的普通功能，而你的内核不满足该门槛，应判定为教程把内核能力误画成了客户端功能，而不是你找错了菜单。全局 `client-fingerprint` 已弃用，需写在 proxy 内；教程仍在“全局设置”里强调该项时，界面差异应视为文档世代不同，而不是漏点了某个未公开按钮。

平台也会造成“菜单缺失”的假象：`disable-keep-alive` 在 Android 上强制为 true；`routing-mark` 仅 Linux；namedpipe 仅 Windows；`find-process-mode` 在路由器上推荐 off。教程若以桌面完整功能集截图，移动端或路由端少若干项是符合手册的，不能据此改写客户端名称。

## 仍无法对应时的下一步

先把当前 YAML 中能与手册逐字对齐的键抄下来，作为“内核身份”证据；再把窗口标题、安装包文件名单独标成“外壳自称”。二者不一致时，以字段为准。若连 YAML 都没有、只有一个与教程完全不同的界面，停止用该教程的菜单路径操作，改为核对外控制地址、是否误把 `/ui` 仪表板当成主程序。路径超出工作目录导致界面资源无法加载时，按手册检查 `SAFE_PATHS`，不要把加载失败解释成版本名称错误。Unix socket 或 namedpipe 能访问却与教程中的密钥步骤冲突时，记住这两种方式不会验证 secret，差异来自访问通道，不是客户端改名。
