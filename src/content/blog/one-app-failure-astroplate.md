浏览器可以访问、同一台设备上的某个桌面应用失败，说明故障通常不在“整机完全不能出网”，而在两类程序是否同样到达代理端口、是否同样通过鉴权、是否使用不同地址族，以及内核是否按进程识别它们。适用条件是同一内核、同一份全局配置下，浏览器工作正常，桌面应用连接失败或行为不一致。不要把运行模式当成第一步去改；应先确认桌面应用有没有连到 Clash 正在监听的 HTTP、SOCKS 或 mixed 代理端口。

## 先确认桌面应用有没有到达同一监听地址

`allow-lan` 为真时允许其他设备经过 Clash 的代理端口访问互联网。`bind-address` 可以是 `*`（绑定所有 IP）、单个 IPv4 或单个 IPv6。`lan-allowed-ips` 默认放行 `0.0.0.0/0` 与 `::/0`，`lan-disallowed-ips` 为禁止段且黑名单优先级高于白名单。判断依据：浏览器在本机成功使用代理端口，只能证明该监听地址对浏览器可达；桌面应用若连到未绑定的地址族，或来源 IP 落在禁止段，仍会失败。步骤：写出桌面应用实际连接的地址，对照 `bind-address`；若应用来自其他设备，检查 `allow-lan` 是否为 true；核对该来源是否出现在 `lan-disallowed-ips`。失败时下一步：让桌面应用改连与浏览器相同的本机可达地址，或把其来源 IP 移出禁止段，然后再讨论 `mode`。

## 核对鉴权、模式和 IPv6 是否把两类程序分开

`authentication` 为 HTTP(S)、SOCKS、mixed 提供用户验证。`skip-auth-prefixes` 设置允许跳过验证的 IP 段，文档示例包括回环地址段。判断依据：浏览器若从可跳过段发起连接，可以不带账号；桌面应用若从其他地址连接且未携带配置中的用户名密码，会被拒绝，表现为只有桌面应用失败。`mode` 为 `rule`、`global` 或 `direct`；选择 `global` 时还需要在 `GLOBAL` 策略组选择代理或策略。已经进入内核的流量按同一模式处理，不能单独解释成“浏览器走规则、桌面应用自动直连”，除非二者根本没有同样入站。`ipv6` 默认为 true，关闭后内核不接受 IPv6 流量；只使用 IPv6 的桌面应用会失败，而仅使用 IPv4 的浏览器仍可正常。步骤：核对该桌面应用是否配置了与入站一致的账号；确认当前模式不是误设为 `direct`；若应用偏好 IPv6，检查 `ipv6`。失败时下一步：为该应用补上鉴权，或把它的来源地址加入跳过前缀，避免用切换 `global` 掩盖入站失败。

## 用进程匹配、日志和传输参数对照浏览器与桌面应用

`find-process-mode` 在 `always` 时强制匹配所有进程，`strict` 由 Clash 判断是否开启，`off` 不匹配进程。判断依据：若你期望按进程把浏览器和桌面应用分开处理，模式为 `off` 时内核不会匹配进程，桌面应用不会得到“按进程区分”的结果。日志级别 `info` 输出一般运行内容以及更高级别信息，`debug` 尽可能输出运行中所有信息，`silent` 不输出，不能用于对照两类程序。`tcp-concurrent` 启用后会使用解析得到的所有 IP 并采用第一个成功连接，两类应用的目标地址集合不同时，结果可以对不上。`interface-name` 与 `routing-mark` 影响内核出站路径；`keep-alive-interval`、`keep-alive-idle`、`disable-keep-alive` 改变 TCP Keep Alive，在 Android 上禁用项强制为 true，对长连接桌面应用更明显。步骤：把 `log-level` 提到足以看到该次连接的级别，确认桌面应用进程是否被匹配，再核查出站接口与 Keep Alive。失败时下一步：临时将 `find-process-mode` 设为 `always` 做对照，然后回到 `strict`；仍失败则检查外部控制器地址只用于 API 管理，不能替代应用入站。
