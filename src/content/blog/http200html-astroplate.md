状态码 200 只说明 HTTP 请求已成功完成，并不保证正文能被 Clash 解析为配置。MDN 对 200 的定义是：请求成功，且成功的含义取决于方法。GET 成功表示资源已取出并出现在消息正文中。正文是什么格式、是否为你期望的订阅文档，不属于状态码的判定范围。因此出现「200 但解析失败」时，应把问题从连通性和认证上移开，转到「这次成功取回的资源到底是什么」。

## 适用条件

仅当订阅请求的最终状态码确实是 200 时使用本流程。若实际是 401、403、404、502、503、504，应先按对应类别处理，不要与解析失败混为一谈。若没有状态码，属于请求未完成。若是 204，没有正文可解析。若是 206，只拿到部分表示，解析失败并不意外。

## 处理步骤与判断依据

1. 核对方法与 200 的对应关系。订阅拉取一般是 GET，200 只证明该资源表示已传输。不要因为 200 就认为配置语法正确或字段完整。
2. 检查到达 200 之前是否有 301、302、303、307、308。303 会改用 GET 取另一 URI。跳转目标若是网站页面，最终仍是 200，解析器则无法把它当配置。判断依据是：最终码为 200，但有效 URI 已不是原来的订阅地址。
3. 排除其它「成功但不可当配置」的 2xx。201 表示创建了新资源，不是取出订阅。202 只表示已接收、尚未处理，HTTP 没有后续异步通知结果的标准办法。203 表示信息可能来自镜像或备份，与源站不完全相同。304 要求继续使用缓存副本，若缓存里是旧网页，解析仍会失败。
4. 不要把解析失败退回到认证流程。必须先认证对应的是 401；代理认证对应 407；网络准入对应 511。已经 200 说明就 HTTP 而言请求已成功，再改凭据通常不会改变正文种类。
5. 若客户端声明了可接受的表示而服务器选不出符合条件的内容，会是 406，而不是「200 却解析乱码」。若把非标准状态码误读成 200，先回到原始三位数字。

判断依据：最终确为 200 且 URI 未跳到页面，问题在正文或缓存；有跳转则先对齐 URI；若实际是 203、304、206，则先对齐源站的完整表示。

## 失败时下一步

仍无法解析时，用能显示状态码和跳转链、但不保存正文的方式复核一次。确认方法是 GET 而不是只拿到头的 HEAD（HEAD 的 200 本来就没有消息正文，无法解析出配置）。向提供者确认该 URI 在 GET 成功时返回的是否为订阅资源本身。在得到可解析正文前，不要用这次 200 的结果覆盖工作配置。
