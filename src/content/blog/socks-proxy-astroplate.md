## 适用条件：哪些失败要从地址与端口两边拆开看

Clash SOCKS 连不上时，应先分清是「应用根本没打到正在监听的地址」还是「打到了错误的端口角色」。官方全局配置把代理端口的访问条件写在 `allow-lan`、`bind-address`、`lan-allowed-ips`、`lan-disallowed-ips` 和 `ipv6`；同时另有 `external-controller` 等 API 监听地址。两类监听用途不同：前者供 http(s)/socks/mixed 代理使用，后者用于 RESTful API。把 API 地址误当成 SOCKS 主机、或把未绑定的网卡地址填进应用，都会表现为连接失败，但原因不在同一层。

本判断适用于：本机应用连本机、局域网设备连 Clash 主机、以及同时开启了外部控制端口的环境。若尚未确认运行模式、认证和日志级别，也不宜把所有失败都归为「端口填错」。

## 偏向地址问题的操作与判断依据

先看 `bind-address`。文档写明其他设备只能通过绑定地址访问：`"*"` 绑定所有 IP，也可绑定单个 IPv4 或单个 IPv6。操作上，把应用里填写的主机与该项逐字对照。判断依据：应用填的是未被绑定的地址，应判为地址错误；绑定了单一 IPv4 却填写 IPv6 字面量（或相反），同样先按地址族不匹配处理。

再看 `allow-lan` 以及两个地址段列表。`allow-lan` 为 false 时，其他设备经过代理端口访问互联网不被允许。`lan-allowed-ips` 仅在允许局域网为 true 时生效，默认 `0.0.0.0/0` 与 `::/0`；`lan-disallowed-ips` 黑名单优先级高于白名单。判断依据：源 IP 不在允许范围或命中禁止列表，失败发生在「这个地址根本不被接纳」，即使端口数字碰巧正确也不应先改端口。

然后看 `ipv6`。该项控制内核是否接受 IPv6 流量，默认为 true。应用使用 IPv6 而配置为 false 时，应按「该地址族的流量不被接受」处理，而不是假设 SOCKS 端口未开启。

认证相关失败有时会被应用显示成连接失败，需要单独排除：`authentication` 作用于 http(s)/socks/mixed；`skip-auth-prefixes` 可让指定网段跳过验证（文档示例含 `127.0.0.1/8`、`::1/128`）。源地址不在跳过列表却未提供匹配的 `user:pass`，应判为验证问题，既不是绑定地址写错，也不是把 API 端口当成了代理端口。

## 偏向端口角色问题的操作、以及仍失败时的下一步

对照 `external-controller`（文档示例为 `127.0.0.1:9090`，也可改为 `0.0.0.0` 监听所有 IP）以及 `external-controller-tls`、Unix socket、Windows namedpipe 等入口。判断依据：应用按 SOCKS 去连 API 监听地址，属于「端口角色用错」——该端口用于外部控制，不是文档所称的代理端口。代理端口是否对局域网开放，仍由 `allow-lan` 与绑定地址约束；API 是否对局域网开放，则取决于 API 自己的监听地址，两者不能互相替代。

若地址侧已能解释失败（未绑定、未允许局域网、命中黑名单、IPv6 关闭），下一步是改正对应项后再让应用重连，而不是改应用里的端口数字。若地址侧全部命中（绑定覆盖该主机、局域网允许、源 IP 未进黑名单、地址族匹配），再核对该应用是否连到了代理端口而非 API 端口，并检查认证是否被跳过。仍无结论时，将 `log-level` 设为 error、info 或 debug，在控制台或控制页面查看失败记录属于拒绝地址、验证失败还是连错监听，再决定改绑定、改名单还是改应用填写的端口角色。
