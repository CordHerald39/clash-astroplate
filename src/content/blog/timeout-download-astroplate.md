http 类型的首次下载和之后的更新，官方写在同一套字段上：用 `url` 和 `header` 发请求，并「经过指定代理进行下载/更新」。页面没有「第一次直连、以后走代理」的分项。第一次能导入、后来更新超时，应对照这些字段在两次之间有没有改过，以及有没有把健康检查超时、更新间隔误认成「更新超时」。

## 适用条件

适用于 `type` 为 http，第一次拿到了代理集合，之后按 `interval` 再拉时失败或一直等待。`file` 只读本地，`inline` 只用 `payload`，不存在对远程 `url` 的第二次更新，不必按本文对照。

## 逐项对照首次与更新

1. `proxy`：下载和更新都经该字段。若首次成功时写的是 DIRECT，后来改成某个代理名，更新超时应先对照这一项，而不是认定 `url` 坏了。
2. `url` 与 `header`：配置里对首次和更新是同一组。对照它们是否被改过。文档没有为第二次请求准备另一条 `url`。
3. `interval`：单位为秒，控制何时再更新，不是单次等待上限。示例 3600 表示间隔到期才会再访问 `url`。把间隔理解成超时，会把「还没到更新点」看成更新失败。
4. `health-check.timeout`：单位为毫秒，只约束节点访问 `health-check.url` 的延迟测试。首次导入后若开启了健康检查，测 Cloudflare 或 Google 超时，和「更新订阅」不是同一件事。对照：本地 `path` 已有文件，只是节点延迟失败，应查健康检查。
5. `path`：首次成功会在 HomeDir 落盘；未填时用 `url` 的 MD5 作文件名。更新超时不等于这份文件消失。
6. `payload`：http 或 file 解析失败时可作为备用代理。有备用节点，只能说明解析失败时仍能加载本地内容，不能说明这次远程更新成功。

## 判断依据

同一份配置下，下载和更新是同一路径。差异应来自 `proxy` / `url` / `header` 是否改过，或把 `interval`、健康检查误当成更新超时。当前还能看到节点，只说明加载源可能是旧文件或 `payload`，不能说明远程更新已经完成。

## 对照完仍超时下一步

先固定用于更新的 `proxy` 与 `url`，不要用加大 `health-check.timeout` 或改 `filter` 去修更新。确认 `interval` 已到期，下载段（经 `proxy` 访问 `url`）可通。远程文件变大时再看 `size-limit`（0 为不限制）。解密问题查 `age-secret-key`，那是拿到内容之后的步骤。文档不规定发放方如何处理旧地址；`url` 本身拉不到时，只能更换 `url` 或 `header`，或向发放方确认地址是否仍有效。
