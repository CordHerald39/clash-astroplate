开了全局模式后某个应用仍像未走代理，通常不是“`mode` 写了 global 就一定会改写该应用的全部连接”。官方对运行模式的定义是：`rule` 为规则匹配，`global` 为全局代理且需要在 GLOBAL 策略组选择代理或策略，`direct` 为全局直连，默认仍是规则模式。全局代理描述的是内核对其已经接收并处理的流量如何选择出站，并不等于操作系统里每一个进程都会自动进入 Clash。某应用不变，应先判断该应用的连接是否进入了代理端口、是否被认证或地址绑定挡住、是否因进程匹配关闭而无法按进程理解，以及 GLOBAL 组是否真的选了出站。

## 先核对 GLOBAL 选择与运行模式是否同时成立

适用条件：配置里已是 `mode: global`，但指定应用的访问路径、解析结果或连接对端没有按你预期的出站变化。判断依据是官方那句“需要在 GLOBAL 策略组选择代理/策略”。只改 `mode` 而 GLOBAL 未选定，全局代理语义不完整。

具体操作：读取全局配置中的 `mode`，确认为 `global` 而不是仍停留在默认 `rule`，也不是误写成 `direct`。然后确认 GLOBAL 策略组已选择代理或策略。若你通过 API 改过策略组，还要理解 `profile.store-selected`：资料写明可储存 API 对策略组的选择，供下次启动使用。应用“看起来没变”，有时是上次储存的选择与这次口头预期不一致，而不是全局模式失效。用外部控制器读取当前选择时，注意 `external-controller` 的监听地址与 `secret`；资料写明 Unix socket、namedpipe 以及在 API 端口开启的 DOH 不会验证 secret，这类入口不适合当作未加保护的核对通道。

## 再判断该应用的流量有没有进入 Clash

某应用不变的第二类原因是连接根本没有经过 Clash 的代理端口。本页与入站范围直接相关的字段包括：`allow-lan`（是否允许其他设备经过代理端口访问互联网）、`bind-address`（`*` 绑定所有 IP，或绑定单个 IPv4/IPv6）、`lan-allowed-ips`（默认 `0.0.0.0/0` 与 `::/0`）、`lan-disallowed-ips`（黑名单优先级高于白名单）。应用若在另一台设备上，而 `allow-lan` 为 false，或源地址落在禁止段，全局模式不会作用于它。

本机应用仍可能被用户验证挡住。`authentication` 用于 http(s)/socks/mixed 代理的用户验证；`skip-auth-prefixes` 设置允许跳过验证的 IP 段，资料示例包括 `127.0.0.1/8` 与 `::1/128`。若应用未提供账密，且其源地址不在跳过段内，连接会在入站阶段失败或改走系统直连，表现为“开了全局也不变”。`ipv6` 控制内核是否接受 IPv6 流量，默认 true；应用若只走 IPv6 而内核未按预期接受，同样会对不上全局代理。

进程维度要单独看 `find-process-mode`：`always` 强制匹配所有进程，`strict` 默认并由 Clash 判断是否开启，`off` 不匹配进程（推荐在路由器上使用）。当该项为 `off` 时，你无法用进程名解释“某应用”，只能退回“该连接是否到达代理端口”。这不能证明全局模式损坏，只能证明当前缺少进程匹配这一判断依据。

## 日志对不上时下一步改哪几项

若 GLOBAL 已选择、入站也允许该源地址，应用仍不变，下一步不要继续堆叠未在本页出现的开关。把 `log-level` 从 `silent` 调整到 `info` 或 `debug`：`silent` 不输出，`error` 仅输出无法使用的错误，`warning` 含不影响运行的错误，`info` 含一般运行内容，`debug` 尽可能输出运行中所有信息。没有日志就不能判断连接有没有进内核。

随后按失败现象分支：认证失败则检查 `authentication` 与 `skip-auth-prefixes`；局域网设备不变则检查 `allow-lan`、`bind-address` 与 IP 段黑白名单；只怀疑某进程则检查 `find-process-mode` 是否为 `off`；只怀疑 IPv6 路径则检查 `ipv6`。确认这些字段后，再用 API 读取 `mode` 与策略组选择是否与文件一致。若读取结果已是 global 且出站已选，而连接日志中根本没有该应用，问题在“未接管”，应回到入站与进程匹配，而不是继续更换 GLOBAL 里的节点。
