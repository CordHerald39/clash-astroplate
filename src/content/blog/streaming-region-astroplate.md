节点能够握手或连通检测通过，只说明该出站隧道可达，不说明当前内容请求被规则送到了这一出站，也不说明 tcp/udp 被正确处理。内容列表、影片或字幕不可用时，应沿 `rules` 从上到下查找「这一次媒体请求实际命中了哪一行」，而不是反复更换节点。

## 适用条件

出站显示可用，但网页或应用内的内容失败；已经排除流量完全未进入 Clash 的情况；怀疑直连、错误代理组、`REJECT`，或 udp 因节点不支持而继续向下匹配。

判断依据：同一出站下普通页面可打开、唯有特定内容失败，更符合规则条件与内容域名、IP 或协议不一致。若所有主机都失败，才优先看表尾 `MATCH` 与默认出站。

## 按规则类型定位命中行

1. 先看优先级。规则自上而下，顶部高于底部。内容主机若被更靠上的 `DOMAIN` 加 `REJECT`、过宽 `DOMAIN-KEYWORD` 或错误 `GEOSITE` 先命中，后面写得再精确也不会执行。必须先指出第一条真正命中的规则。
2. 再看域名类是否对准内容主机。`DOMAIN` 要求完整相等。`DOMAIN-SUFFIX` 不匹配中间插入字符的域名，文档示例是 `google.com` 不匹配 `content-google.com`。`DOMAIN-WILDCARD` 仅支持 `*` 与 `?`，且与配置其他位置的 Clash 格式通配符不同。账号域、网页域与 CDN 拉流域经常不是同一后缀；拉流域被送到 `DIRECT` 或 `REJECT`，就会表现为节点正常但内容不可用。
3. 看 `GEOSITE` 是否覆盖真实请求。它只匹配 Geosite 内域名。内容若走未收录的第三方主机，仅写类别出站不会覆盖该主机，请求会落到后面的 `GEOIP` 或 `MATCH`。
4. 看 IP 类规则与解析时机。`GEOIP` 匹配目标 IP 所属国家代码，`IP-ASN` 与 `IP-CIDR` 同样看 IP。内容域名可能解析到与品牌国家不同的 CDN。`no-resolve` 会跳过为匹配目标 IP 规则而做的 DNS 解析；前面没有任何解析时，IP 规则可能被跳过并落入 `MATCH`。若更早规则已经解析，后面即使写了 `no-resolve` 仍可能用已有 IP 命中，表现为「以为跳过、实际命中了 `GEOIP` 直连」。
5. 看协议。`NETWORK` 可匹配 tcp 或 udp。请求为 udp 且节点没有 udp 支持时，会继续向下匹配。点播检测走 tcp 正常、实时传输失败时，应检查是否命中 `NETWORK,udp` 或落到不支持 udp 的出站后又滑走。`DSCP` 仅限 tproxy 的 udp 入站，不能用来解释普通入站上的点播失败。
6. 看进程与入站限制。独立播放器、浏览器、Android 包名分别对应 `PROCESS-NAME` 与 `PROCESS-PATH`。只放行浏览器路径时，播放器内容不会进同一出站。`IN-TYPE`、`IN-NAME`、`IN-USER`、`IN-PORT` 限制入站；内容走了另一入站名称时，会像「节点正常、应用不行」。
7. 看逻辑规则、子规则与集合。`AND`、`OR`、`NOT` 括号误用会导致条件恒真或恒假。`SUB-RULE` 进入子表后，不能再用主表后续条目的直觉去解释。`RULE-SET` 未有效引用时，等于该行不存在，内容会掉到更下方。
8. 看 `MATCH`。它无需条件、匹配全部剩余请求。找不到更具体命中时，内容不可用应首先核对 `MATCH` 指向的出站是不是你以为的那条链路。

## 失败时下一步

命中 `REJECT`：先改该条或调整顺序，不要换节点。命中 `DIRECT`：核对 `GEOIP`、`GEOSITE`、`DOMAIN-SUFFIX` 是否把内容主机当成直连。命中代理但 udp 继续下滑：检查 `NETWORK` 与节点 udp 能力，再看下一条。主机名完全对不上：回到完整域名，而不是加更宽关键字。逻辑规则无法判断：拆成单条验证命中后再组合。目标是定位内容请求的命中行与出站，而不是比较节点延迟。
