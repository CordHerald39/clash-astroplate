集合加载成功，表示该代理集合已经得到节点列表；健康检查失败，表示随后的延迟测试没有在设定条件下完成。文档把取集合和健康检查分成不同字段，因此“provider 已更新”不能当成“节点已通过检查”。适用条件是：http 或 file 已解析成功，或解析失败但已用 payload 作为备用代理，同时 health-check.enable 为 true。处理时应围绕检查地址、超时、期望状态和懒惰状态，而不是反复下载同一份集合。下面按排查顺序给出判断依据和失败后的下一步。

## 先确认不是名单被筛空

加载成功之后，节点仍可能被 filter、exclude-filter、exclude-type 改写。前两项按关键词或正则留下或排除，多个正则可用反引号区分；exclude-type 按竖线分割的类型排除，且不支持正则。若筛选后集合为空，检查没有对象，表现为得不到有效结果，这与单次超时不是同一原因。判断依据是：集合内容表明加载已有节点，并且筛选后仍有剩余，才进入检查层。override 只覆写节点字段，例如名称前后缀或通用出站字段，它的成功也不等于延迟测试通过。若名单明显不对，应先改筛选三项，而不是加大检查频率。

## 再按健康检查字段逐项核对

enable 必须为真，否则不会做延迟测试。检查地址必须写在 health-check.url，不能误用成集合下载地址。interval 为检查间隔，单位秒，只决定多久测一次，不决定单次是否成功。timeout 为超时，单位毫秒；若把毫秒当成秒来理解，会误判“已经等了很久仍失败”。lazy 默认为 true：不使用该集合节点时不进行测试。此时没有新结果，并不等于检查失败，需要先判断该集合是否处于被使用状态。expected-status 对照响应状态，状态不符合期望时，即使有响应也应视为未满足检查条件。官方将健康检查称为延迟测试，判断依据只能是：测试有没有发出、有没有在超时内结束、状态是否符合期望。更新集合的 interval、下载用 proxy、header、path、size-limit 服务的是取文件，加载已成功时它们不是优先排查项。

## 失败时的下一步与不要改错的地方

建议顺序如下。第一，确认 enable 已打开。第二，确认当前确实在使用该集合，以避免懒惰状态直接跳过测试。第三，单独核对检查地址、超时单位和期望状态是否与你的预期一致。第四，看检查间隔是否很长，从而把“还没到下一轮”误写成一直失败。不要用改 path、size-limit、header 或更新用 proxy 去“修复”已经加载成功的集合。不要用收紧 filter 来掩盖超时，除非这些节点本来就不该留在名单里。若只有部分节点失败，说明问题落在延迟测试层，应保留筛选规则，继续对照超时与期望状态。若全部没有测试动作，优先怀疑 lazy 与 enable，而不是订阅更新周期。payload 仅在解析失败时作为备用内容；加载已成功时，改 payload 不能处理检查失败。把结论写成“延迟测试未在超时和期望状态下完成”，避免写成集合未加载。
