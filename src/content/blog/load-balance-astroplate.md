当不同请求走出不同出口时，应先检查策略组通用字段是否正在改变当前可用集合或默认选中项，而不是先改路由规则。适用条件：出口确实由某条 `proxy-groups` 配置决定，并且能用 `name` 与必须的 `type` 定位到该组。检查目标是解释变化来自名单、默认选择、健康检查还是筛选。

## 检查类型、引入方式与默认选中

第一步确认 `type` 仍是你以为的那一种。类型是必须字段，写错或被覆盖会直接改变选择行为。第二步拆引入：`proxies` 是出站代理或其他策略组；`use` 是代理集合；`include-all`、`include-all-proxies`、`include-all-providers` 会按名称排序纳入节点。其中 `include-all` 不含策略组，`include-all-providers` 会使引入代理集合失效。若两次请求之间集合内容变了，按名称排序后的第一项也会变，出口变化可以完全来自排序。

第三步看 `default-selected`。为空或节点名不存在时，默认选择组中第一个节点。判断依据：如果当前出口正好是排序后的第一项，应优先怀疑默认选择回退。组名含特殊符号时要用引号包裹，否则可能根本没有解析到你正在查的那一组。场景步骤：列出该组最终节点名，标出第一项，再与 `default-selected` 对照；三者不一致时，先修正这一层，再观察后续请求。

## 检查健康检查是否改变了可用集合

出口在请求间跳动时，把健康检查当作集合过滤器来查。`url` 是测试地址，且只会检查 `proxies` 里的代理，不会检查 `use` 引入的代理集合节点。因此：若可见出口来自 `proxies`，状态变化可能来自探测；若出口来自 `use`，组级探测本来就不会覆盖它们，应到集合侧或上游组去查，而不是反复改该组 `url`。

`interval` 不为 0 才定时测试，单位秒。`lazy` 默认为 true，未选择到当前策略组时不测试。组刚被选中前后，可用状态可能突然更新，表现为一开始一个出口、随后换了。`timeout` 单位毫秒，超时会记失败。`max-failed-times` 默认 5，超过触发一次强制健康检查，可能在连续失败后集中改写可用集合。`expected-status` 若已配置，必须状态码一致才可用；可用斜线与短横写多码或范围。判断依据：若探测地址返回的状态不在期望里，节点会从可用集合消失，后续请求只能落在仍可用的其他出站上。默认星号则不对状态做要求，这时更应查超时与失败次数。

## 检查筛选、空组与弃用字段，失败时下一步

`filter`、`exclude-filter` 会按关键词或正则改变集合，仅作用于引入代理集合以及引入所有出站代理。`exclude-type` 按类型排除引入的出站代理，无视大小写。集合侧名字变化时，原来稳定的出口可能被筛掉。组为空时走 `empty-fallback`，默认 `COMPATIBLE`，且不能填代理组名，只填 proxy 名称；若误填组名，空组回退不会按设想工作。`disable-udp` 只影响 UDP，TCP 请求出口变化不要用它解释。`hidden` 与 `icon` 只影响 api 展示。`interface-name`、`routing-mark` 在组上已弃用，出口网卡或标记异常应查节点级配置，优先级为代理节点大于代理策略大于全局。

失败时下一步：列出最终节点名，标出第一项与 `default-selected`；标出每个节点来自 `proxies` 还是 `use`；标出 `lazy`、`interval`、`expected-status`。若变化节点仅存在于 `use`，停止在该组 `url` 上打转。若第一项因 include 按名排序而改变，先固定名单来源再谈请求差异。若集合为空，核对 `empty-fallback` 是否为合法 proxy 名。
